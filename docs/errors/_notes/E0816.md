A site has a `mail` block, but the block cannot produce a working sender, so
`liyasa` minted a sign-in link and had nowhere to send it. The reader sees the
same "check your email" page either way — the endpoint answers identically
whether or not an address is known, on purpose — so nothing on the site will
tell you this is happening.

## Fix it

The message names the key. Four things produce it:

- **`mail.from` or `mail.replyTo` is not an address.** It is read as an email
  mailbox, so `Docs <docs@example.com>` and `docs@example.com` both work and
  `docs at example.com` does not.
- **`mail.smtp.password` does not resolve.** It holds a *reference* —
  `secret:<name>` or `env:<VAR>` — never the password itself. `env:` reads the
  environment of the process running the server; `secret:` reads this
  instance's encrypted secret store, and reports separately when the instance
  has no store at all.
- **`mail.smtp.username` is set and `mail.smtp.password` is not, or the other
  way round.** Half a credential authenticates as nobody, so it is refused
  here rather than at the relay.
- **`seo.canonicalOrigin` is unset.** The link has to be absolute: an email
  client has no page to resolve a relative one against.

A block that works looks like this:

```json
"mail": {
  "from": "Docs <docs@example.com>",
  "smtp": { "host": "smtp.example.com", "security": "starttls",
            "username": "docs", "password": "env:SMTP_PASSWORD" }
}
```
