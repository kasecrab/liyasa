A screen reader announces a control by its name. This one has none, so it is
announced as "edit text" or "combo box" and nothing else, and a reader who
cannot see the label beside it has no way to know what it is for.

`liyasa test --a11y` raises it per control per page, from the built HTML rather
than from the Markdown, because whether a control ends up named depends on what
the theme and the component rendered around it.

## Fix it

Give the control a name in any of the four ways the check accepts. A visible
label is the best of them, because it helps everyone rather than only the people
using a screen reader:

```html
<label for="q">Search the docs</label>
<input id="q" type="search">
```

When there is no room for visible text, name it directly:

```html
<input type="search" aria-label="Search the docs">
```

`aria-labelledby` pointing at an existing heading, and `title`, are also
accepted. A submit or button input is named by its `value`, and a hidden input
needs no name, so none of those are reported.

This is the static half of the accessibility checks. The other half needs a real
browser and catches the cases a string scan cannot: a label that exists but is
hidden, a name that is empty after styling, a control moved out of its label by
script. Install the companion runtime to get it ([`E0003`](/errors/E0003)).

Related: [`E0305`](/errors/E0305) for an image with no alt text,
[`W0306`](/errors/W0306) for a skipped heading level. See
[accessibility](/guides/accessibility).
