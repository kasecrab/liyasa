`verify.http.staging.auth` names a credential and Liyasa could not turn it into
an `Authorization` header, so the request was not sent and the check did not
run.

The check reports this rather than going out unauthenticated, because an
unauthenticated request against a staging endpoint is worse than no request at
all: the endpoint answers `401`, and a block that asserts `status=401` — auth
pages often do — then passes while proving nothing about the credential. A
green run would be evidence of nothing.

## Fix it

The message names which of the two happened.

If it says the setting is not a secret reference, `auth` holds something other
than `secret:<name>`. Liyasa never reads a credential out of `liyasa.json`,
because a token in the config file is a token in the repository:

```json
{ "verify": { "http": { "staging": {
  "baseUrl": "https://staging.example.com",
  "auth": "secret:staging-api-token"
} } } }
```

If it names a secret the store does not have, add it — `liyasa secret set
staging-api-token` locally, or the same name in the deploy environment's secret
store — or clear `verify.http.staging.auth` if that target needs no credential.
Check for a typo first: the name in the config and the name in the store must
match exactly.

A secret whose value already names its scheme (`Basic …`, `Token …`) is sent as
written; anything else is sent as `Bearer <value>`. A block that sets its own
`Authorization` header keeps it, so a sample demonstrating an expired token
still goes out with that token.

See [E0635](/errors/E0635) for other unreadable `verify` settings, and
[verification](/guides/verification).
