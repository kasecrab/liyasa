An entry in `auth.operators` names a subject that this instance's sign-in will
never issue, so the person it was meant to elevate stays a reader and nothing
says why.

An operator is matched on the subject their session carries, which is not their
email address unless the identity provider happens to use one. OIDC and JWT
carry the provider's `sub`; a personal access token carries whatever minted it;
a magic-link reader carries a per-instance salted hash of their address, which
nothing outside the instance can predict; and the shared site password issues
one subject for every reader, so it names a mode rather than a person.

## Fix it

Sign in as the person you want to elevate and read the subject their session
carries, then put that string in `auth.operators`:

```json
{ "auth": { "mode": "oidc",
            "operators": [{ "subject": "8f14e45fce", "role": "owner" }] } }
```

Under `mode: "password"` there is no such string and there never will be — no
reader can be told apart from another — so an instance that needs a dashboard
operator needs a mode that identifies people. Magic-link sign-in has the same
limit for a different reason: the subject is a hash of the address, not the
address.

See [W0138](/errors/W0138) for magic-link sign-in with nowhere to send the link.
