A verified fence names a file or a snippet that could not be read, so the check
was reported rather than run.

Running it anyway is the one thing Liyasa will not do here. A sample whose
fixture is missing, or whose `expect-file` was never read, still runs — it just
answers a different question from the one the fence asked, and reports pass or
fail as though it had not.

## Fix it

The message names which attribute and which path.

For `fixture="data/input.csv"` and `expect-file="out.txt"`, the path is relative
to the project root and the file has to be committed — a fixture in
`.gitignore` works locally and fails in CI:

````markdown
```shell {verify fixture="data/input.csv"}
wc -l data/input.csv
```
````

For `setup="login"`, the snippet is `snippets/login.md` — the same namespace
`{% snippet "login" %}` uses, so one snippet can serve a page and a check. Check
the file exists and that its fenced blocks are in the language the check runs.

See [E0609](/errors/E0609) for an attribute whose *value* Liyasa cannot read, as
against a value that names something absent, and
[verification](/guides/verification).
