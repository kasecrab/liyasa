# E0817

**Preview protection cannot be satisfied by this configuration**

| | |
|---|---|
| Severity | Error |
| Area | Server, auth, deployments, network |
| Raised by | `liyasa-server` |

This instance serves a preview, `auth.preview.protection` asks for a protection
it cannot provide, and nothing the reader does can satisfy it.

A preview link reaches CI logs, notification emails and everyone with read
access to the repository, so the failure has to be loud at startup. On the
running site it looks like an ordinary page — or an ordinary sign-in prompt —
and nothing tells an operator that the protection they asked for is absent.

## Fix it

**`protection` is `org` or `password` and `auth.mode` is `public`.** This is the
serious case: a public site mounts no auth at all, so there is no session to
require and no password form to present, and the preview is served to anyone
holding the link. Configuring a password does not help, because there is nowhere
to enter it. Set `auth.mode` to the flow your readers use — `jwt`, `oidc`,
`password` or `managed` — or accept a public preview by saying so:

```json
"auth": { "mode": "public", "preview": { "protection": "public" } }
```

**`protection` is `password` and no password is set for this environment.** The
site has a login flow, so nothing is disclosed, but every request answers with a
sign-in that cannot succeed. The password is per environment (AUTH-02), so a
production password does not protect a preview: set one for the environment this
instance serves.

Production is never affected. `auth.preview` describes previews only, so the
same configuration is silent on the production deployment.

Related: [E0803](E0803.md) when the `auth` section itself does not parse,
[E0816](E0816.md) when `mail` is configured and cannot send.
