# W0818

**A site route is shadowed by the MCP server endpoint**

| | |
|---|---|
| Severity | Warning |
| Area | Server, auth, deployments, network |
| Raised by | `liyasa-server` |

This site publishes a page, asset or redirect at `/mcp`, `/_liyasa/mcp`,
`/.well-known/mcp` or `/.well-known/mcp.json`, and `liyasa serve` answers those
addresses with the MCP server instead. Your page is still built and still in
`dist/`; it is unreachable on the running site.

The MCP endpoint is an explicit route and pages are served by the fallback, so
the endpoint wins — silently, and without this warning nothing would say so. The
address is not negotiable: every generated `llms.txt` publishes
`MCP server: <origin>/mcp` to agents, so serving something else there would
break the contract the site itself advertises.

## Fix it

Move the page and redirect the old address:

```json
"redirects": { "rules": [{ "source": "/mcp", "destination": "/guides/mcp" }] }
```

A redirect rule is resolved before the route table, so it keeps working for
anyone who saved the old link — but note that it does **not** win over the MCP
endpoint either. `/mcp` itself stays the server; redirect a different path *to*
your page, and link to the new address from your navigation.

If the page really is about connecting to this site's MCP server, the endpoint
answering there is arguably right, and the fix is to name the page something
else — `/guides/mcp`, `/integrations/mcp` — rather than to fight for `/mcp`.

To have no MCP server at all, turn it off; the warning goes with it, and so does
the line in `llms.txt` that advertises the endpoint:

```json
"agents": { "mcp": { "enabled": false } }
```

Only the four exact addresses above are taken. `/mcp/setup` and anything else
under `/mcp/` is an ordinary page: the endpoint is one URL, not a prefix.

Related: [`W0130`](W0130) for a page that is served but no navigation reaches,
and [`E0105`](E0105) for two pages claiming one route.
